# Test First Implementer

## Overview

Use this skill to implement an approved slice with RED-GREEN-REFACTOR discipline: prove the desired behavior is missing, make the smallest change, then verify it.

## Hard Rules

- Do not implement without an approved slice plan or explicit task scope.
- Do not broaden scope beyond the slice, even if nearby improvements look tempting.
- Do not write production behavior before a failing automated test, failing check, or documented failing manual verification exists.
- Do not treat tests written after implementation as equivalent to test-first work.
- Do not overwrite unrelated user changes.

## Required Inputs

Prefer an implementation prompt generated by `vertical-slice-planner`. Before editing, identify:

- slice goal and acceptance criteria
- in-scope and out-of-scope behavior
- relevant files or subsystems
- expected interfaces or data contracts
- automatic and manual verification commands
- subagent instructions, if any
- final response requirements

If any of these are missing and cannot be inferred from repo docs, ask or stop with the missing decision.

## Workflow

1. Load context: read `AGENTS.md`, relevant docs, the approved slice plan, and the minimal files needed.
2. Check state: run `git status --short` and avoid touching unrelated changes.
3. Follow subagent instructions from the plan. If none are provided, keep work local unless the user explicitly asks for subagents.
4. Create or identify the smallest verification that should fail before the change.
5. Run that test/check/manual probe and confirm it fails for the expected reason. If it passes, stop and report that the behavior may already exist or the check is wrong.
6. Implement the smallest code/docs/config change that can pass the check.
7. Run the targeted check again. Fix only failures caused by the slice.
8. Refactor only after green, and only inside the slice boundary.
9. Run the smallest relevant broader verification from project docs.
10. Summarize changed files, RED evidence, GREEN evidence, remaining risks, and skipped checks.

## Verification-First Fallback

If the project has no practical automated test path for this slice:

- define the observable pre-change failure first, such as missing CLI output, failing smoke command, absent UI state, or reproducible manual step
- capture the command or manual steps before editing
- run the same check after implementation
- explain why an automated test was not added

Prefer adding a small automated test when it is reasonable and consistent with the project.

## Subagent Handling

Use subagents only when the approved plan explicitly calls for them or the user asks. Preserve ownership boundaries:

- read-only explorers may inspect docs, APIs, logs, or tests
- workers may edit only their assigned files or modules
- parallel workers must not edit the same files
- the main agent owns integration, conflict resolution, final verification, and final report

If the plan says not to spawn subagents, do not spawn them.

## Output Report

Finish with:

```text
What changed:
RED check:
GREEN check:
Broader verification:
Skipped checks:
Remaining risks:
Recommended next step:
```

Mention exact commands and outcomes. If a command failed, include the cause and whether it was fixed.

## Common Mistakes

- Starting implementation from the plan without first proving the check fails.
- Expanding the slice into adjacent cleanup or architecture work.
- Adding mocks that test the mock instead of behavior.
- Treating manual clicking as enough when an automated check is easy.
- Ignoring subagent ownership boundaries and causing overlapping edits.
- Reporting success without exact verification evidence.
